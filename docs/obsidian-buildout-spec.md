# dayGLANCE Obsidian Build-Out

**Status:** Draft, revision 1
**Date:** 2026-08-10
**Scope:** Extending dayGLANCE's Obsidian integration from direct filesystem access to a full bridge, including a first-party Obsidian community plugin.

**Current position (2026-09-01): between Phase 7 and Phase 8.** Phases 0–7 are
built and deployed. The fleet is running at poll cadence with SSE nudge
consumption gated off by default (§3.10, seventh record) while the audit-fix
backlog is squashed and the fixes soak. The re-arm sequence — remaining
breaker fixes, a supervised single-machine re-arm, then the fleet, then
default-on — precedes Phase 8, whose scope now lives in
`obsidian-companion-spec.md`.

---

## 1. Purpose

dayGLANCE's Obsidian integration currently works by reading and writing vault files directly. That approach is fast, private, and requires no plugin or server, and it should remain the default wherever the platform permits it.

It has two limits:

1. **Platform coverage.** Direct filesystem access is unavailable on iOS entirely, and on Safari, Firefox, mobile browsers, and tablet PWA installs.
2. **Sync propagation.** Obsidian Sync only runs while Obsidian is open. Changes dayGLANCE writes to a vault while Obsidian is closed do not propagate to other devices until Obsidian is next launched on the originating machine.

This document specifies a phased build-out addressing both, plus the format and correctness work that should precede any expansion of write surface.

## 3. Decisions of record

These were arrived at rather than being obvious, and are recorded so they are not relitigated by accident.

### 3.1 GLANCEvault only, no WebDAV path for advanced features

The basic direct-filesystem integration continues to work for everyone regardless of sync backend. Everything specified from Phase 5 onward assumes GLANCEvault.

**Rationale.** Supporting both transports in the plugin roughly doubles its configuration surface and support burden for a solo maintainer. GLANCEvault is expected to become the default for all self-hosters running GLANCE apps.

**Consequence.** The plugin becomes another device in a GLANCEvault account and inherits per-device credential binding, account-scoped route enforcement, quota accounting, and individual credential revocation with no new server work.

### 3.2 The plugin is authoritative where installed and paired

If the bridge plugin is present and paired to GLANCEvault on a device, the plugin owns the vault on that device and dayGLANCE does not write directly.

**Rationale.** Installing a plugin is a deliberate act, so a behavior change is not a surprise. A single ownership rule is far easier to document and debug than a capability-negotiated split.

**Critical qualifier: paired, not merely installed.** Obsidian Sync propagates installed community plugins across devices when that option is enabled, which most users leave on. A single deliberate install on one device therefore lands the plugin on others without a second deliberate act. An unpaired plugin must be inert: direct access continues, plugin does nothing. Authority transfers on successful pairing.

**Amended (Phase 6 ruling): pairing granularity is per-vault, not per-device — "installed and paired" means *per vault-copy where the plugin runs*.** The plugin's credentials live in its `data.json`, which rides Obsidian's plugin-settings sync to every copy of the vault. Per-device credentials in a fleet-shared file would be either one token pretending to be many identities or every device's token visible in every copy — both worse than being honest about the actual unit. So one pairing pairs the plugin wherever that vault's copies run, every copy presents the same credential, and revocation is vault-wide: revoke the device token server-side and re-pair (which also rotates the subkey — §3.4/§3.12). Authority is still *evaluated* per reading device — each dayGLANCE install honors the heartbeat of the vault copy it can see — but the paired identity behind that heartbeat is the vault, not a device.

**Dependency the per-vault ruling assumed without writing down (field incident, 2026-08-31):** `data.json` reaches a device only through Obsidian Sync's community-plugin-settings sync — a user-toggleable setting that can flip without notice (observed: it turned itself off on one device). When it does, that vault copy's plugin loses its credentials, beats `paired: false`, and the device falls back to direct mode — SAFE (an unpaired plugin is inert by this ruling's own qualifier, and direct mode is the designed fallback), but the fleet silently splits between modes, and before the per-device bridge status indicator the only way to notice was opening plugin settings on each device individually. So: the per-vault ruling propagates *conditionally*, the condition is a setting the user can flip, and the running system must keep the resulting per-device state legible — the three-state bridge status block (active-and-paired / plugin running but NOT paired here, with the plugin-settings-sync check named as the known cause / no plugin detected) exists for exactly the middle state. `components/BridgeStatusPanel.jsx` (native devices), `components/BridgePairingPanel.jsx` (desktop).

### 3.3 Pairing state is carried in the heartbeat payload

The plugin writes `.dayglance/heartbeat` on an interval while Obsidian is open. Payload: `{paired, accountId, deviceId, ts}`.

**Rationale.** Arbitration only matters on devices where dayGLANCE could write directly, and on precisely those devices dayGLANCE has vault access and can read the file. *(Corrected: this rationale originally continued "On iOS there is nothing to arbitrate and correspondingly no way to read it" — written before the native iOS ObsidianBridge existed. iOS has had bookmark-scoped vault access — heartbeat reads included — since that bridge shipped, so arbitration covers it like any other vault-access platform.)* The genuinely vault-less platforms are the sandboxed browsers (Firefox/Safari web), where no direct write can happen and there is nothing to arbitrate. The mechanism degrades exactly where it is irrelevant, and no separate signalling channel is needed.

**Revert path.** A stale or missing heartbeat resumes direct writes, treated identically. Staleness threshold should be comfortably longer than an Obsidian restart, so minutes rather than seconds.

**`deviceId` semantics (Phase 6 note).** The wire key `deviceId` predates the per-vault pairing ruling and is kept — the payload shape is final. Its semantics are *per vault-copy install id*: minted once per plugin install into `data.json`, which Obsidian settings-sync shares across the vault's copies exactly as it shares the pairing. It identifies which vault copy is beating (the heartbeat file itself never syncs, so liveness stays local), not a paired device.

### 3.4 HKDF bridge-scoped subkey, never the root E2E key

The plugin is provisioned with a bridge-scoped subkey derived via HKDF from the root sync key, and the Obsidian intent stream is encrypted under that subkey.

**Rationale.** The plugin's settings live at `.obsidian/plugins/dayglance-bridge/data.json`, in plaintext, inside the vault, which Obsidian Sync propagates to every device. Obsidian's mobile plugin runtime has no keychain equivalent. Storing the root key there would put the entire dayGLANCE dataset at risk from a single leaked vault file. A scoped subkey limits the blast radius to the Obsidian bridge stream.

Combined with per-device credentials on the transport side, a compromised vault costs one revocable device credential and one scoped stream, not the account.

**Additional mitigations.** Recommend excluding the plugin data file from Obsidian Sync in documentation. State plainly in the plugin settings tab what is stored where. The plugin source is public under community directory rules, so this design will be read by people who care.

### 3.5 Block IDs are a hard prerequisite for Phase 6

Phase 2 must be complete and running long enough that most vault content carries IDs before Phase 6 begins.

**Rationale.** The transport handoff is the risky moment. At cutover the vault may contain tasks dayGLANCE wrote via direct access that GLANCEvault holds under different identity. With `^dg-` IDs that reconciliation is a scan-and-match. Without them it is text matching across two sources of truth, which is the shape of the duplication bugs addressed in PRs #1146 through #1148.

### 3.6 Semantic intent stream, not reuse of the FSA handle shim

Phase 6 does not add a third implementation behind `obsidianElectronHandle.js`. dayGLANCE and the plugin exchange semantic task and note changes over a bidirectional GLANCEvault intent stream.

**Rationale.** A GLANCEvault-backed handle would satisfy the write path cleanly but has nothing to read unless the plugin maintains a mirror of vault content in GLANCEvault, which is real storage and real staleness for little benefit. dayGLANCE already knows its own task state from GLANCEvault; the only thing it needs from the vault is Obsidian-side edits, which arrive as inbound intents. This is a fork of the reconcile path rather than a reuse of it, but a smaller one than maintaining a mirror, and the boundary matches the ownership rule in 3.2.

**Reversibility note.** This is the most reversible decision in the plan. If Phase 6 work repeatedly wants to change shared logic in `src/obsidian.js`, that is the signal to reconsider, and it is much cheaper to unwind early.

**Amended (Phase 6 ruling): the stream is semantic *outbound* and observational *inbound* — a deliberate asymmetry, not an oversight.** Outbound (dayGLANCE → plugin) intents are semantic operations (`task_append`, `task_state`, `task_retitle`, `daily_note_write`, `wiki_note_write`): dayGLANCE knows exactly what changed and why, and a pure `(current file, intent) → new file` application is what makes convergence provable. Inbound (plugin → dayGLANCE) is *observations* — the plugin reports the latest observed file state per path, never inferred edits — because inferring semantics from raw vault edits is precisely the job dayGLANCE's scan-and-merge pipeline already does: per-field adoption, base diffing, and every §3.10 ownership ruling apply to an observed file unchanged, regardless of how the bytes arrived. An inbound "semantic" stream would re-implement that pipeline inside the plugin and create a second place where ownership rules live, which §3.10 exists to prevent.

### 3.7 Filename portability: refuse creation, permit writes to existing files

The validator rejects the union of characters illegal on any platform an Obsidian vault may sync to: `[ ] # ^ | * " \ / : ? < >`, control characters `0x00-0x1F`, leading dot, trailing dot or space, and Windows reserved device names (case-insensitive, including with extensions).

Existence is checked **before** the validator gate. An invalid name that already exists is written to normally; an invalid name that does not exist is refused.

**Rationale.** The portability harm is entirely in creating a new unportable name. A file already in the vault is already breaking sync on other platforms whether or not dayGLANCE writes to it again. Refusing that write buys zero portability and leaves the user with a permanent error on a task whose linked note visibly exists.

**Honest framing requirement.** Obsidian's own restrictions are OS-specific and narrower than this union. As of v1.8.10 Obsidian forbids `[ ] # ^ |` on all platforms plus `\ / :` on macOS/iOS/Linux, `* " \ / : | ?` on Windows, and `\ / : * ? "` on Android. Characters like `?` and `*` are perfectly creatable Obsidian note names on macOS. dayGLANCE is deliberately stricter, on portability grounds, and the error copy must say so rather than implying Obsidian would have refused.

**Rejected alternatives.** Sanitizing illegal characters breaks round-trip, because `readWikiNote` resolves links by exact-name search and would never find the sanitized file again; rescuing it with frontmatter aliases adds alias-aware resolution and collision handling for little gain. Renaming the offending file and rewriting the wikilink is worse still, since renaming breaks every other link to that note across the vault, and backlink maintenance is Obsidian's job.

### 3.8 Community directory submission comes after dogfooding, not before

The plugin runs unlisted (BRAT or manual install) through Phases 5 and 6. Submission to the Obsidian community directory happens once the codebase is stable.

**Rationale.** Nothing about running the plugin on your own devices requires the directory. Obsidian's automated review scans every version, not just the initial submission, and a failed release is removed from search within 24 hours. Submitting a thin plugin and then substantially rewriting it means putting each intermediate state through that gate for no benefit.

### 3.9 Staged vault-format rollout: read-support first, containment as the safety net

**Standing rule, not a one-time decision.** Any change to what dayGLANCE WRITES into the vault ships in two releases: first a release whose parser fully understands the new format but never emits it, then a release that enables emission. The gate is a build-time constant (`src/utils/obsidianWritePolicy.js`), never a user-facing setting: a setting pushes correctness onto the user, and someone always has a device they forgot about.

**Ordering discipline, not a guarantee.** Read-support-first is the right default for every vault-format change because it maximizes the share of the fleet that understands a new format before anything emits it. But release ordering **cannot be enforced** — a Docker user pulls `latest` after six months and skips every intermediate release, so "the reader has propagated" is a state nobody can observe and no release sequencing can produce. Read-first must not be relied on as a gate; it narrows the exposure window, nothing more.

**Rationale for the exposure being worth narrowing.** The fleet spans five platforms on three release channels (dev, Developer ID, MAS, Play, App Store/TestFlight) whose store approvals never align, plus always-on appliances with vault access that lag behind updates. A client that does not understand a format token reads it as **title text**, hashes it into a brand-new content-derived id, and imports a duplicate that syncs fleet-wide — stable duplicates for the whole mixed window, surviving the update in the heavy-stamp case (analyzed for `^dg-` block ids, then observed live 2026-08-26).

**Containment is the actual safety net.** Before any format's emitting release ships, evaluate whether a naive old parser's misread of that format is **self-identifying** — the way a `^dg-` token swallowed into a mangled title still names the very task it duplicates. Where it is, build containment: recognize the misread at every sync ingress AND at boot (PR #1457's fourth wiring point — a device that never syncs never repairs itself), derive the correct identity from the corruption, and retire the duplicate so it stops propagating and the minting device self-repairs on update. Where a misread would NOT be self-identifying, that is a design signal against the format as proposed — prefer a shape whose corruption carries its own antidote.

**Standing consequence (found during Phase 4 planning, not designed for): the `^dg-` token is a universal self-identifying carrier.** Since the write release (#1458), every task line dayGLANCE writes carries a block-id token — so ANY line-level format we ever write rides a line whose misread is already self-identifying: a pre-block-id parser swallows the decoration AND the trailing token into a mangled title, producing a ghost row whose token still names its successor, and #1457's containment holds unchanged because its rule 4 hashes the FULL mangled text, decorations included. The per-format containment question for line-level formats is therefore answered by inheritance, not per-format design. Limits to remember: the inheritance covers only formats written ONTO TASK LINES (frontmatter and note-body formats have their own, simpler story — a naive parser ignores non-task lines); the ghost redirect sanitizes only the token, so a newer ghost's decorated mangled title can sit in the app title cosmetically until the next retitle; and the guarantee is only as strong as the containment tests, so a new written format should still add a decorated-ghost case to them.

**Read support means the FULL read semantics, not "strip and ignore."** A device that strips a token but still derives the old identity (e.g. hashing the clean title into a legacy id) keeps re-producing retired identities after a write-release device retires them — a milder seed of the same divergence. The read release carries everything except emission: recognition, identity adoption, bridging, dedup rules.

**Fleet-readiness gating: investigated and declined.** A per-account readiness gate (capability bundle in the sync payload, a GLANCEvault devices endpoint, cursor cross-referencing to detect stale clients) would make the ordering enforceable — and was deliberately not built: substantial permanent server-and-client surface for a solo maintainer, to close a gap that containment reduces to a bounded, temporary, self-healing inconvenience confined to the un-updated device's own screen. Recorded here so it is not rediscovered as a novel idea later.

**Applies next to Phase 4** (Tasks emoji metadata, Dataview inline fields, frontmatter) — a strictly larger write surface than block ids: each of those formats gets a read release before any device emits it, and each gets the containment question asked, format by format, before its emitting release.

**The plugin is part of the mixed-fleet problem, and it is the WORST-updated member (recorded 2026-08-31, from the field).** The bridge plugin has no auto-update during unlisted dogfooding — every fix requires hand-copying a rebuilt `main.js` to each desktop's vault plugin folder and reloading Obsidian, and a machine forgotten in that round is a machine running OLD IDENTITY LOGIC against a shared vault. Observed consequence, day one after the timescale-guards fixes: an updated Mac left a merge-corrupted line alone (the `^dg-`-anywhere rule) while a pre-fix plugin on another desktop, observing the same vault through Obsidian Sync, re-stamped it — the exact compounding the fix closed, re-opened by version skew alone. This is the same staged-rollout exposure this section exists for, and it caught a fully-controlled fleet; the general lesson is that "the fleet" includes every Obsidian install with the plugin enabled, not just every dayGLANCE install. Mitigations that exist today: plugin-side changes that only REFUSE actions (skip rules, write gates) degrade safely under skew — a stale plugin does old harm, never new harm from the fix — so identity-affecting plugin fixes should keep the paired dayGLANCE-side half (as fix 3 did with `blockIdSuffix`), which auto-updates and can refuse to compound what a stale plugin writes. *Corrected from the field (2026-08-31, next morning): the fleet DOES have an auto-update channel during dogfooding — Obsidian Sync's "installed community plugins" sync carries `main.js` itself, so a rebuilt plugin copied to ONE desktop's vault propagates to every synced desktop. Two caveats keep this record's spirit: a running Obsidian does not hot-load updated plugin files — each device executes the old build until its Obsidian restarts (the per-device tell is the bridge panel's stamping line, which only a new build's heartbeat carries) — and it is the same sync toggle whose silent flip stripped the pairing in the data.json incident, so it is load-bearing in both directions. The deploy checklist becomes: rebuild, copy once, let Sync settle, then restart Obsidian on each desktop as it is next used, verifying the stamping line.* BRAT or directory distribution (auto-update proper) still arrives with the §3.8 submission milestone.

### 3.10 The ownership model — the seven rulings in one place

Seven ownership rulings landed across Phases 3, 4, and 6. Each was made deliberately, with its reasoning recorded where it landed; this section exists so the MODEL is legible in one place instead of seven. The rulings are coherent because they all answer the same question — *whose record is this?* — and the answer differs by what kind of thing the value is, not by which side touched it last.

**1. The vault owns titles.** (Two-sided retitle policy, Phase 3 / #1465; `utils/obsidianTitleConflict.js`.) A title is user-authored content and the vault line is its document. One-sided edits resolve silently in the editor's favor; a two-sided conflict is won by the vault, with the dayGLANCE rename preserved as a durable record in `task.notes` — a lost sentence needs preserving.

**2. The vault owns the metadata fields it demonstrably edited.** (Per-field vault-edit adoption, Phase 4 Step 2; `vaultMetadataEdits` in `src/obsidian.js`.) Mapped Tasks metadata (due, scheduled, priority) adopts from the vault when — and only when — the field's serialized value actually changed in the line since our last observation, detected by the same base comparison the title policy uses, at field grain. An untouched ⏳ sitting in an edited line never clobbers a dayGLANCE reschedule; add, change, and REMOVE all adopt; the same-field two-sided race resolves vault-wins, consistent with titles. **Deliberately without a notes record** — a decision, not an oversight: a lost priority is one of four values, re-set with a tap, and the vault's version is still visible on the line; a lost sentence of prose is neither. The rejected alternative (first-import-only mapping) recreated exactly the failure mode rejected for 🔁 — a user annotates an imported task in Obsidian and dayGLANCE silently does nothing. Read support that only reads once, at first import, doesn't do what its name promises.

**3. dayGLANCE owns completion timestamps.** (Completion-timestamps feature / #1470.) App wins when it has a value; the vault marker fills the blank. A completion timestamp is dayGLANCE's own record of an action dayGLANCE performed, and the vault marker is an *echo* of it — letting a stale echo overwrite the source would be backwards. The adoption case (marker present, app blank) is import, not conflict.

**4. dayGLANCE owns task state.** (The founding rule, pre-Phase-2: "Obsidian controls task existence and initial values.") Completion is OR-merged, and scheduling, colors, durations, notes, subtasks, project links and the rest belong to the app once a task is imported — except where rulings 1–2 carve out the line-derived values the vault demonstrably edited.

**Correction record (2026-09-02) — owned scheduling is enforced in the vault, not only in memory.** Ruling 4 says dayGLANCE owns scheduling once a task is imported, and the merge enforced it by copying DG's time over the line's in app state. But the WRITEBACK only fires on a DG-side transition — it diffs the task against a snapshot — and the post-scan snapshot was built from the merged, already-DG-valued task, so a line whose time disagreed with DG's read as "no change" and was never written. The field case: the y0bm31lo war ate the writeback of a DG-side move (10:15 → 09:30), leaving the line at 10:15 and DG at 09:30 with nothing left to trigger a write, indefinitely and silently — ownership true in memory, false in the file the user reads. *The rule now:* the scan and observation pipelines report a line that CARRIES a time different from DG's (`lineSchedule`), and the writeback snapshot records the LINE's time for that task (`utils/obsidianWritebackSnapshot.js`); the ordinary writeback diff then sees DG's time as a change and writes it through the existing path — no new write code, the same latch, pattern, and commit-on-enqueue discipline. Consequence, deliberate: a time edited by hand in Obsidian is reverted on the next scan. It was already discarded from DG state under this ruling; the vault now shows the ruling instead of hiding it. Narrow by design: only a line that carries a DIFFERENT time; an untimed line of a DG-scheduled task is not a different time and is left alone (its own ruling, if ever); a vault ⏳ edit the merge adopts under ruling 2 makes the two agree and reports nothing, so adoption and enforcement cannot fight. The rejected alternative — adopting the line's time as a "demonstrable edit" like ⏳ — has no record of what DG last wrote to the line (the leading time is not part of the raw title), so it cannot tell a vault edit from a lost writeback, and it would carve scheduling out of DG ownership in a second place. Pinned by `obsidian.ownedScheduleEnforce.test.js`.

**5. The vault owns existence, and the recycle bin loses to it — visibly.** (Bin-versus-vault, Phase 6; `utils/obsidianBinRestore.js`.) A task binned in dayGLANCE whose line still exists in the vault is restored from the bin, with the reason attached to the task. This is ruling 4's founding clause executing correctly — the vault controls task existence, and the re-import IS that rule; the bug was never that the vault wins, it is that it won silently and repeatedly (the bin copy's deliberately-fresh delete stamp beat the re-import's epoch `lastModified` in the cross-list reconciler, which deleted the imported copy every cycle while the next scan resupplied it — a #1455-class delete/resupply loop). Bin-wins was rejected because it would mean dayGLANCE suppressing a line that exists in the user's file — the app deciding a vault line shouldn't count, the shape refused throughout — and would require a tombstone channel the vault never sees (there is no delete intent by the Phase 6 scope ruling): exactly the split-brain state the availability note below warns about. The honest cost, accepted: binning is an explicit user action and telling the user no is unfriendly; but the alternative is a line sitting in their daily note that dayGLANCE deliberately ignores forever, which is the invisible divergence vault-is-ground-truth exists to prevent. Surfacing follows ruling 1's precedent (#1465): the restored task carries a durable line in `task.notes` — lighting the card's notes button on the exact object the user is confused about — plus a transient toast. The un-bin necessarily repeats while the line exists, but the notes record is deterministic and idempotence-guarded, so repeated binning (or N devices racing) never stacks a second entry. In plugin mode the restore fires when the note is next observed (observations are per-changed-note), the same availability bound as deletion detection. This ruling is the clearest illustration of the model's through-line: the vault owns existence, and where dayGLANCE disagrees, dayGLANCE explains rather than overrides.

**Correction record (2026-09-01) — the cross-list survivor rule.** The restore, as first built, had a hole and the scan tier had a latent war primitive; together they produced a single-machine delete/resupply war (`obsidian-dg-y0bm31lo`, the war guard's first live catch). *The hole:* the restore indexed only the scan pass's own output and placed the un-binned copy by `_deletedFrom` with a stamp fresher than everything, without asking whether a LIVE copy of the id already existed in the other list. The user had two copies (a scheduled one and a project-card inbox one), binned the inbox copy, and the restore resurrected it beside the live one — a second live copy with the winning stamp. *The primitive:* the scan's merge context built its lookup in two passes and let the inbox pass silently overwrite the scheduled entry, leaving the id in BOTH move-sets; routing then inverted against the line (a scheduled-shaped line became an inbox record carrying a `startTime`), and the outer merge dropped the copy the DB tier had just chosen to keep. The DB tier (`reconcileCrossList`, newest-wins) and the scan tier resolved the same collision in opposite directions, each undoing the other every cycle, indefinitely, with no peer involved. *The rule now:* (i) a bin entry whose id is still live in app state, either list, is a binned duplicate — dropped and reported as `superseded`, never restored (ruling 5 is untouched for a task whose ONLY copy was binned); (ii) an id live in both lists is resolved by the scan exactly as the DB tier resolves it — newest `lastModified` wins, ties to the scheduled list per `CROSS_LIST_PRIORITY` — so both tiers pick the same copy and the state converges in one cycle. The alternative, the line's shape deciding, was rejected because it leaves the DB tier disagreeing whenever the newer copy sits in the other list: the same war with the polarity flipped. Membership in a list is evidence of a user's move only when it is unambiguous. Pinned end to end by `obsidian.crossListWar.test.js`, which replays the field objects through the real parser, context, merges, and reconciler and asserts a one-cycle fixed point.

**6. Existence divergence is judged at the vault's statement time — the note's mtime.** (Revival stamping, Phase 6; `reviveScannedAgainstTombstone` in `utils/mergeObsidianTasks.js`.) **The tombstone question is an EXISTENCE question, and the honest timestamp for "does the vault say this line exists" is the note's mtime — the vault's statement time. The task record's `lastModified` answers a different question: content LWW. Those two questions happened to share a field, and that is what made the documented "a later re-creation in Obsidian wins" rule nominally true but mechanically inert for tasks** — a fresh import carries an epoch `lastModified`, so a line deleted and retyped verbatim (same content hash; or, for a stamped task, the deterministic `deriveBlockId` re-minting the tombstoned token — the come-back-then-vanish flicker) lost to its tombstone until the 60-day GC, a latent direct-mode trait that note-scoped inference (the availability note below) made common. The ruling: when a SCANNED row — a line the batch actually read out of its note — would be dropped by a tombstone OLDER than that note's mtime, the row is admitted with `lastModified` lifted to the note mtime, in that one case only. The lift is what makes the revival propagate: the revived row out-LWWs its tombstone at the `applyEngineData` gate, the `mergeSync` cleanse, and the push guard with no changes to any of them. **This makes the documented rule actually true, which is ruling 4 (the vault controls existence) working rather than being amended.** Two recorded rejections, because both will be proposed again: *(i) stamping every fresh import with its note's mtime* — epoch on fresh imports is LOAD-BEARING: a bare re-parse carries none of the app-only fields (projectId, color, notes, assignedUserSyncIds, completedAt), so an mtime-stamped default-filled copy from a cold-open or vaultless device would beat another device's real record in row-level LWW and wipe those fields fleet-wide; epoch guarantees a parse never beats a record — don't change it, and note that WIDENING the revival condition beyond "tombstone exists AND the note was written after it" reintroduces exactly this hazard; *(ii) clearing the tombstone key on reappearance* — `deletedObsidianKeys` merges grow-union, newest-per-key, so a local removal is re-added by every other device's copy; removals structurally don't stick in that channel, and out-timestamping the tombstone is the only durable win. Retained rows are deliberately not revived (their notes are not in the batch, so there is no fresh vault statement to lift from); a stamped task transiently dropped that way returns on its note's next observation, which the stamp's own write guarantees exists.

**7. The plugin stamps before it reports — NORMALIZE-THEN-OBSERVE.** (Phase 6, the duplicate-class closer; `stampUntaggedTaskLines` in the shared package, wired in the plugin's `emitObservation`, gated by the config row's `blockIdWrites`.) **This is the class-level fix, and the record should say why. All four duplicate incidents share one root — an untagged line existed long enough for something to act on it. The three prior fixes each repaired a layer: bookkeeping (#1482, #1490), guard evidence (#1492), janitor (#1491's note-scoped inference). This removes the root: with the plugin stamping before reporting, no observation dayGLANCE receives contains an untagged task line, so "visible in dayGLANCE" structurally implies "already stamped" with no timing involved. Racing to stamp faster can never close the window, because visibility precedes the round trip by construction — that kills the alternative rather than merely losing to this one. And the "identity assignment in two places" objection doesn't survive inspection: `deriveBlockId` is deterministic from (date, rawTitle) precisely so any number of minters agree unanimously. The policy stays in one place — the shared package. Only the trigger exists in two.** *Consistency with §3.6, stated explicitly rather than carved out: stamping is not interpreting. It writes a fact — a derived, unanimous block id — and then reports state. It never classifies an edit as a rename or a delete, which is the thing §3.6 was drawn to prevent; observations still report file state and nothing else (the state now includes a token the plugin wrote, which is a real vault fact). The boundary moves where identity assignment FIRES, not where it's defined.* Mechanics that keep it safe: parse parity is the stamper's contract (it lives beside `parseTasksFromMarkdown` and stamps exactly the lines the parse would import untagged, deriving from exactly the parse's rawTitle — otherwise unanimity breaks in the race window against the backstop); **the WRITE RULE (corrected — see below): never write a note whose editor buffer differs from disk; write open-clean notes through an EDITOR TRANSACTION (`planStampInsertions`, the stamper re-expressed as per-line edits so the two paths cannot diverge — an editor transaction composes with concurrent typing instead of racing it, eliminating the check-then-write window rather than narrowing it); write closed notes through `Vault.process` (no buffer exists to clobber). Dirty is detected DIRECTLY — `MarkdownView.getViewData()` is the live buffer, unsaved keystrokes included, so buffer ≠ disk IS the condition — and a dirty note defers the stamp AND its observation together (unstamped state is never reported), uncapped: deferral is bounded by human behavior, since Obsidian's own save lands ~2s after typing pauses and clears the condition. A clean buffer is necessary but not sufficient — the CURSOR GATE (the fifth lesson, below) additionally defers any line holding a live cursor, because a save certifies a pause, not a finished line.** The write gate is FAIL-CLOSED: stamping requires the config row's `blockIdWrites` to be exactly `true` — no config row seen, or a row from a build predating the field, means no stamping, because not stamping is recoverable (the backstop covers it) and stamping against the user's setting is not. dayGLANCE-side stamp-on-sight STAYS as the backstop, deliberately not removed as redundant: it covers everything the plugin isn't positioned to see (plugin closed, mobile vault), and direct mode is unchanged. Lines dayGLANCE already imported untagged still resolve through the existing hint adoption and the stamped-orphan sweep.

**The write rule is a corrected ruling, and the correction itself is the record (the 2026-08-31 truncation — this project's first and only unrecoverable data loss).** *What was claimed:* the stamp fired on the observation debounce, "≥2s after the note's last save, when the editor buffer is normally clean," deferred while the note was the FOCUSED editor file, capped at ~10s, then stamped anyway via `Vault.process`; the recorded residual said a dirty-buffer merge might at worst drop *our token*, which would re-stamp on the next save. *Why it was wrong — and the generalizable lesson, which matters more than the cap value:* **the ≥2s-after-save mitigation fired exactly when it was least safe. Obsidian DEFERS saves during sustained typing, so "2 seconds since the last save" is satisfied precisely when the buffer is maximally dirty — a timing heuristic keyed to the wrong event is not merely imprecise, it can be ANTI-CORRELATED with the condition it is meant to detect.** Past the cap, `Vault.process` — atomic against *saved* state only, structurally unable to see the buffer — stamped the last mid-word save; Obsidian reloaded the open note from disk and the user's unsaved keystrokes were destroyed, truncated mid-word with the token appended after the truncation (and the note-scoped inference then correctly tombstoned the full-text task whose line no longer existed — every layer behaved as specified; the cap's specification was the bug). The "token dropped at worst" claim is RETRACTED: the dirty-buffer reconcile can discard the USER'S side, which is the unrecoverable side. The focus proxy also had a blind spot the real rule closes: a dirty note in a BACKGROUND pane was never protected at all. *What replaced it:* the real condition instead of the proxy — dirty by direct buffer-versus-disk comparison, uncapped deferral, editor-transaction writes for open notes — chosen on the trade the cap got backwards: starving dayGLANCE of a note someone is typing in is recoverable; destroyed keystrokes are not. **This is the third time in this project a proxy stood where the real condition was available — after gate (a)'s enumerated triggers (the rule was "every identity move," not a trigger list) and gate (b)'s baseline clearing (the evidence was archivable, not disposable). The pattern is the thing worth remembering: when the real condition is readable, read it.**

**The sibling lesson — cycles versus wall-clock (the 2026-08-31 SSE-speed war, the day after the truncation).** Same family as the proxy lesson, recorded beside it deliberately: **a guard expressed in cycles is a guard whose meaning changes when someone speeds up an unrelated path.** Phase 7 shipped no ownership change and no guard change — it changed the TIMESCALE, shrinking "one cycle" from minutes to ~2 seconds — and three things that were safe at 30 seconds were not safe at 1 second, composing into a two-device feedback war (`s34iqu ↔ dg-` round trips every ~1.5s, tokens auto-merged into the middle of titles, 429 storms) in which every layer behaved per spec. The three, and their fixes, one commission: *(1) intent applies wrote raw into live editors* — at poll speed an intent landed minutes after the user's attention had moved on; at SSE speed it landed ~1s after the dayGLANCE action, exactly when the Obsidian buffer is most likely dirty, and Obsidian's auto-merge became a corruption engine (fixed by extending ruling 7's write rule to `applyOne`: dirty defers, the drain retries — the same rule, the shared dirty check, not a parallel one; and the stamper/`blockIdSuffix` now refuse any line carrying `^dg-` anywhere, so a merge-corrupted line can never be compounded by either minter — damaged lines are a human's). *(2) The deletion confirmation hold counted fetches* — "commit on the NEXT successful fetch" implicitly meant "minutes later" under the 5-minute poll; at SSE speed the janitor OUTRAN the replication it was waiting for, committing mid-flight cross-device states as deletions (fixed: the hold is ≥90s of WALL-CLOCK absence plus a subsequent complete fetch — independent of cycle speed by construction: faster cycles re-check absence more often, never conclude it sooner). *(3) The retire/tombstone pair had no oscillation breaker* — the guard's conservative refuse-then-heal was self-correcting at a cadence where humans and Obsidian Sync converged between rounds; at trigger speed it became one half of a perpetual loop (fixed: the retirement-heal breaker, `#1455`'s streak shape — three same-entity heals in ten wall-clock minutes while the retirement's successor stays tombstoned-not-live — LATCHING to an error rather than cooling down, because that contradiction does not resolve by waiting). The rule going forward, stated once here rather than per-incident: **when the real unit is wall-clock time — replication convergence, human editing rhythm, "long enough that this cannot be the same event" — use wall-clock time. A cycle count is a time proxy that someone will eventually invalidate by making cycles faster, and they will be changing an unrelated path when they do.** A code sweep at fix time found the remaining cycle/count-denominated guards and they are NAMED in the fix PR rather than silently converted — the two worth watching are the plugin's `HWM_PERSIST_GAP` (a data.json persist gap denominated in seq units, sized in the comment as "a normal editing day", which the account-global seq rate can compress) and the own-ack rings (64 entries standing in for "an echo arrives within seconds").

**The fifth lesson — PREMATURE IDENTITY ASSIGNMENT (2026-08-31, the "W ^dg-...atch tennis" line; the cursor gate).** Same family as the proxies, one door down: **the stamp trigger fires on save-plus-debounce, and a save certifies a PAUSE, not a finished line.** Obsidian autosaves precisely at pauses, and a pause mid-word is common. The incident: the user typed `21:15-21:45 W` and paused mid-word ("Watch"); the buffer went clean; the stamper — correctly, per every rule then in force — minted identity for the fragment (`21:15-21:45 W` is a perfectly valid task line to the parse) and the editor transaction appended the token at the line's end, which WAS the cursor position; resumed typing landed after the token, splitting the word around the stamp (`W ^dg-bi3n2qafatch tennis on ESPN`). **Stated explicitly: no write rule was violated.** #1498's rule correctly answered "is it safe to write now" and the answer was yes — the buffer was genuinely clean and nothing was destroyed. The question that went unasked was whether the line was FINISHED — the trigger treated "saved" as a proxy for "complete." *The fix (the cursor gate, `partitionStampPlan` in the shared package, wired in the plugin's open-clean stamp path):* skip any plan entry targeting a line that currently holds a LIVE editor cursor, and defer that line to the next pass. Scope decisions of record: **per-line, not per-note** (a "no open editor" rule would effectively stop stamping — leaving notes open is normal — and reopen the untagged-population problem normalize-then-observe exists to solve); **no cooldown** ("don't stamp a line edited in the last N seconds" is the proxy version of this condition, and proxies now have three recorded instances of aging badly); **deferral resolves on its own** (the cursor moves when the user clicks elsewhere or switches away — no timer, no cap). One definitional decision made at build time, stated as a deviation because the commission's mechanism needed "cursor" made precise: a live cursor is one that can actually RECEIVE keystrokes — an editor with focus. Parked cursors in background tabs are deliberately NOT honored: a parked cursor never moves on its own, and because ruling 7 couples the stamp and the observation, honoring it would defer the whole note's reporting indefinitely for the commonest entry pattern (type a line, switch away, cursor left resting at its end) — the exact starvation the per-line scope was chosen to avoid. The accepted residual: a mid-word switch-away-and-back can still split a word around a stamp — rare, humanly bounded, and inert afterward (the `^dg-`-anywhere rule keeps either minter from compounding the damaged line; it imports untagged and waits for a human).

**The sixth lesson — THE CONFIG-NULL FAIL-OPEN HOLE (2026-08-31, later the same night; the fragment factory).** Ruling 7's invariant — no observation dayGLANCE receives contains an untagged task line — turned out to be CONDITIONAL on a cache nobody had named as load-bearing. The plugin's copy of the `meta:config` row lived in memory only, refreshed solely when a drain paged over the row; after any plugin reload the row's seq sat below the persisted drain cursor and was never re-listed, and the dayGLANCE side's publish-once guard was PERSISTED in localStorage, so even "restart dayGLANCE" could not republish it. With config null, `bridgeConfigAllowsStamping(null)` is false — correct, fail-closed, exactly as designed — but the gate guarded the ENTIRE normalize-then-observe block: stamping, the write rule, the cursor gate, AND ruling 7's stamp/observe coupling. The report itself still ran. **Fail-closed for writes had silently become fail-open for reporting**: the plugin shipped unstamped, mid-typing daily-note states at autosave cadence, and dayGLANCE imported each pause as a task ("Testing to see if Claude knows" arrived as three fragments). The diagnosis was also this project's costliest, because the state was INVISIBLE — every panel showed a healthy paired bridge while the one fact that mattered (this plugin has no config) had no surface anywhere; a remote-observer hypothesis and a workaround built on a misread guard both had to be falsified by the user before the code was read closely enough. *The fixes, each aimed at a different leg:* the plugin PERSISTS the config beside the cursor it rides under (`BridgeState.config` in data.json) and recovers it by a single-row GET per pairing generation when null, so config-null can only mean a fresh pairing's first seconds; daily-note REPORTING now fails closed while config is null — the report waits, re-armed per path, making ruling 7's invariant unconditional rather than conditional on a cache; the publish-once guard moved to module memory, keyed on (pairing generation, value) — every dayGLANCE session republishes once, so a republish is always REACHABLE, and a re-pair's rotated subkey (under which the old sealed row is unreadable) republishes too; and the invisible state got a surface — the heartbeat carries a stamping tri-state (`armed` / `off` / `no-config`) that both bridge panels render, with `no-config` loud. The lesson, stated for the next cache: **a fail-closed gate is only as closed as the path it gates — when one condition guards several coupled obligations, verify that failing it disables ALL of them or NONE, and name every cache whose loss changes an invariant's truth.**

**The seventh record — THE DB-TIER RETIRE/TOMBSTONE WAR (2026-08-31, the same night's third incident; the tripwire exercised).** The fragments' cleanup collided with their retirement bookkeeping and produced a war one tier DOWN from the vault-file wars: dayGLANCE's own DB sync, at ~2s a round while Obsidian ran. Three interlocking pieces, each per-spec in isolation, verified against logs and the engine source: **(1) the resurrection primitive** — the engine's push has no delete POLARITY: `pushDirtyRows` re-classifies each dirty id at push time by mirror presence, the pull runs BETWEEN the snapshot diff that authorized a delete and that push, and a push never advances the pull cursor, so the device's own pushed rows re-list on every pull — the pull re-supplied the "deleted" row into the mirror and the blessed delete silently flipped into an upsert (`written:2 deleted:0` on a delete-only dirty set; the client's own WRITE LOOP detector named the `upsert -> delete -> upsert` shape); **(2) the re-mint edge** — stamp-on-sight re-derived the SAME dg successor for each resurrected legacy row (determinism is the unanimity feature everywhere else), re-recording the retirement and re-creating a successor row the tombstones killed at the next apply boundary; **(3) the trigger fuel** — each round's writes produced seqs the maxSeq-only own-ack ring couldn't cover, so SSE nudges ran the loop at trigger speed (closing Obsidian froze it to poll cadence — the plugin's intent-consumption deletes were the metronome). Fix 4's retirement-heal breaker never fired: it guards the SKIPPED/heal arm, and these rows propagated as `retired`/`tombstoned` every cycle. *The fixes:* **the re-mint refusal** at the minting site (`isTombstonedRemint`: a derivation whose retirement is already on the record with the successor tombstoned-not-live is a completed identity move, not a new one — refuse loudly; a live successor or a tombstone-less absence still mints); **the polarity reassert** post-pull (`reassertPropagatedDeletes`: weigh each pull-resupplied copy against the evidence that authorized its delete — tombstone still at-least-ties → evict the copy so the push stays a delete; genuinely newer → the flip IS correct newest-write-wins); **the delete-propagation streak latch** (the same id delete-propagated a 4th time in 10 wall-clock minutes latches for the session — the shape-agnostic wall for the propagate arm, so the NEXT composition of correct rules hits it without needing its own diagnosis first); and **own-ack coverage for every seq** (the server emits one nudge per batch but one per `deleteRow`; the engine's client now records each delete ack's seq, not just the folded max). And per the Phase-7 assessment's tripwire — three wars in one night is a new class, not a named leftover — **dayGLANCE's SSE nudge consumption now defaults OFF** (`sseNudgesEnabled`, localStorage escape hatch `dayglance-sse-nudges`), reverting to the 5-minute/2-minute polls and the plugin's 30-second drain until these breakers are proven against live traffic; the plugin's own SSE stays, since every war cycle must pass through dayGLANCE's drain.

**The seventh lesson — PREMATURE IDENTITY ASSIGNMENT, THE CROSS-DEVICE ARM (2026-08-31, the fleet's first stamping-armed morning; the "13: ^dg-q6wlym0v" line).** The fifth lesson's incident, one ring out — and it only became REACHABLE the first morning the whole fleet ran stamping-armed simultaneously, which is worth stating as its own sub-lesson: a guard proven on one device is unproven against the fleet. The incident, token-verified: the user typed three keystrokes of a new task line on one desktop; Obsidian Sync shipped that mid-composition snapshot within seconds; a second desktop found the fragment closed/clean/cursorless — every local rule satisfied — and minted identity for it (`deriveBlockId('2026-08-31','13:') = q6wlym0v`, the exact token on the corrupted lines); the stamped write synced back into the author's DIRTY buffer, where Obsidian's auto-merge anchored on a fuzzy `13:` context and spliced the token into the WRONG line. **The cursor gate could not reach this by construction: it is local — device B cannot see the cursor on device A.** "Clean and cursorless on B" is anti-correlated with "finished on A" during active cross-device typing — the fifth lesson's proxy critique verbatim, with the real condition now unreadable in principle rather than merely unread. *The rule considered and rejected, recorded because the refutation is a mechanism:* stamp only lines observed byte-identical across two passes, no clock. It fails on a receiving device because between Sync deliveries the file is FROZEN — the deferral re-arm loop (2s) re-reads identical bytes trivially, so "unchanged across two looks" is evidence about Sync's delivery quantization, not about the line; it would have replayed the incident at +4s instead of +2s (the frozen-bytes trace). The identity requirement itself survives the refutation — it is what makes the waiting EVIDENCE rather than cooldown — but it needs a floor to straddle a delivery. *The adopted rule (`settleStampPlan`, `STAMP_SETTLE_FLOOR_MS`):* a receiving-posture device stamps a new untagged line only on byte-identical re-observation at least 10 seconds after first record; any change re-records and restarts the wait; state is memory-only (nothing rides data.json) and pruned each pass to lines still in the stamp plan. **The floor is a MECHANICAL constant — sized to Obsidian Sync's delivery quantum (save-gated shipping plus network), not to typing psychology — and that distinction is what keeps it from aging the way the ≥2s-after-save mitigation did.** *The scoping that resolves the felt-latency objection:* the hold applies ONLY where no local editor has focus. Where this device holds the live composition surface, the cursor gate and the buffer-vs-disk dirty check are strictly better evidence and already ruled — the authoring device stamps seconds after the cursor leaves the line, unchanged; the ten seconds lands exclusively on devices nobody is typing at, whose imports are poll-paced anyway. *Starvation shapes, recorded honestly:* (i) a line some tool rewrites continuously never settles, and per ruling 7 it defers its whole note's OBSERVATION indefinitely — same acceptance as the cursor gate's residual, with the bound being "the line stops changing" rather than "the human moves the cursor"; visible in the console if it occurs. (ii) The tail NO finite floor closes: a mid-word pause that ships a fragment, followed by more than the floor of continuous typing (Obsidian defers saves during sustained typing), keeps a receiving device frozen past any T — true of the rejected 15-second timer too. The floor under that tail is the `^dg-`-anywhere containment, which this incident demonstrated working: the corrupted line was inert, visible, and non-compounding — a human fixed two lines and the system never made it worse. *Addendum (field-tested the same evening; ruled recorded-not-built-against): the tail includes REPLICA DIVERGENCE.* A mid-typing snapshot stranded by an immediate quit (Obsidian Sync's upload does NOT reliably flush before quit — a test-procedure assumption falsified in the field) leaves the fragment as the vault's ONLY reachable truth: the receiving devices' bytes are then not merely frozen but genuinely correct, so settling and stamping them is defensible-forever behavior no stamping rule on any device could improve — the authoring replica meanwhile holds its own finished, self-stamped line offline. The corruption enters on RECONNECT, through Obsidian Sync's character-level splice-merge of the two divergent replicas (`Test ^dg-9gbev5xzing again to see what's up ^dg-592baea0`, both tokens verified against deriveBlockId) — a merge outside every write path of ours, and one that mangles any line edited on both sides of an offline gap, tokens or no tokens. Why recorded rather than built against: the trigger requires quitting Obsidian within seconds of typing a new line (the field instance was a deliberately adversarial test procedure); unanimity even prevented a double stamp (both receiving devices mint the identical token, the second finds the line tagged); recovery was one hand-edit, after which the fragment task GC'd through note-scoped deletion on its own and the damaged title healed by ordinary retitle flow; and the only visible mitigation (never stamp a note's most-recently-modified line) is a proxy of the family this project has now retired three times.

The through-line: *user-authored content follows its editor; dayGLANCE's own records follow dayGLANCE; and "the vault edited it" is always established against a stored base observation, never assumed from mere difference.* Any change to these rules is an ownership decision and a hard stop, per the standing rule.

**Identity versus content (Phase 6, the untagged-rename fix).** Obsidian is authoritative for task CONTENT — but identity is a different question from content, and conflating them is what made untagged lines fragile. An untagged line's only identity is its own text (the content-derived hash id), so ANY inbound edit to it is structurally delete+create: the task fractures on the first rename, whoever made it. Stamping (`^dg-` block ids) is how dayGLANCE keeps track of a line whose content Obsidian owns — those aren't in tension; the stamp asserts nothing about the words on the line, only that they stay one task. The requirement stated plainly: **a task should survive any manipulation from either side — title changes, reschedules, attribute changes, user assignment, colors, completion — and stay one task.** Phase 2's opportunistic rule (stamp on the task's next *edit-triggered* write) left every not-yet-edited import in the fragile window; **STAMP ON SIGHT** closes it by assigning identity on FIRST IMPORT. This is deliberately a **named new write-trigger class — the identity-assignment write fired by import**: dayGLANCE writes to the vault as a consequence of merely reading it, a class stated in the open (its own trigger condition in the writeback, its own record here), never slipped into the change detection. It rides the ONE existing emit site (the writeback effect), so gate (a)'s commit-on-enqueue rule covers it with no new machinery, and it is double-gated: plugin mode only (`authoritative` — the direct writers arm launch-on-write at fire time, so a machine-initiated direct stamp could pop Obsidian open with no user action behind it; direct mode also already janitors untagged renames via the vault-wide detector; a direct-mode stamp-on-sight waits for a machine-write flag through the launch chokepoints — a named follow-up, not an omission), and on the same `blockIdWritesEnabled` release as every stamp — it is Phase 2's stamp with a widened trigger, not a second minting policy. Timing: the stamp fires on a writeback pass explicitly nudged after the importing cycle's merge lands (the sync-in-progress guard skips the effect run the merge itself triggers); the seconds-wide residual — a line renamed before its stamp lands — is caught by the note-scoped deletion inference below, and the plugin's apply keeps the operation idempotent. The composition also retro-cleans pre-existing orphans: stamping a surviving line rewrites its note, the observation comes back, and the note-scoped inference tombstones the fractured leftover. *(Amended by ruling 7 — normalize-then-observe: while paired, the PLUGIN stamps before reporting, so stamp-on-sight is now the BACKSTOP — kept deliberately for everything the plugin isn't positioned to see: plugin closed, mobile vault, and the direct-mode follow-up above.)*

**Availability note (Phase 6, from the gate (b) correction).** The ownership model has an implicit precondition that only became visible when a mode existed where it failed: **"the vault controls task existence" (ruling 4) holds only while something is actually detecting existence changes.** The rulings say who *wins*; they silently assume some machinery is *looking*. Phase 6's plugin mode stops a device's direct scans, and its first-draft transition handling (clear the detector baseline) would have left the expected end state — every vault-access device paired — with no deletion detector running anywhere, suspending ruling 4 fleet-wide without any rule having been "changed." The archive-and-reconcile amendment (Phase 6 build record, gate b) restores detection across the paired window. The durable lesson: any future mode that changes *which machinery observes the vault* must state explicitly which ownership rulings its observers keep enforceable, and a ruling with no enforcer is suspended in fact whatever this section says. That check belongs in the mode's design review, before the next mode arrives.

*Amended (Phase 6, the untagged-rename fix): the gap is now CLOSED AT THE NOTE GRAIN.* Observations can never establish scan completeness, but each one is the plugin's read of a WHOLE file — complete truth for the one note it covers. Note-scoped deletion inference (`utils/obsidianNoteScopedDeletions.js`) runs while paired: a task claiming to live in an observed note (`obsidianFileDate`, or the date baked into a legacy id) whose parse carries neither its id nor its legacy hint is tombstoned through the existing `deletedObsidianKeys` LWW channel — stamped at the observation's file mtime (never "now", mirroring the archive-reconcile's archive-time stamping, so an app edit newer than the note wins), and only after the WALL-CLOCK confirmation hold: ≥90s of continuous absence plus a subsequent complete fetch (the note-scoped analog of the detector's incomplete-scan conservatism; it exists for the cross-note move, whose two observations a fetch can split — and whose second half can lag by REPLICATION, not just emit order). *(Originally a one-cycle hold; converted after the 2026-08-31 SSE-speed war made "one cycle" mean ~2 seconds — see the cycles-versus-wall-clock lesson in ruling 7's correction record.)* *(Amended again by audit fix C1: the hold's continuity is now itself verified — the pending store records when reconcile last ran, a gap beyond the poll cadence (mode flip, app restart, Obsidian closed, re-pair) restarts every pending clock, and a successful direct scan clears the pending set outright, because "90 seconds of absence" is only evidence while something was watching for the id to reappear.)* **What remains open:** a note never observed while paired still reports nothing — deletion there waits for the next direct-mode scan (the archive-reconcile). *(A second residual originally recorded here — a line removed and re-created verbatim staying suppressed until the tombstone GCs, because epoch-`lastModified` fresh imports made the channel's documented re-creation revival inert for tasks — was a latent direct-mode trait that note-scoped inference made common, and is now FIXED by ruling 6 above: revival stamping at the note's mtime.)* **Named assumption this leans on**, the same way the vault-wide detector always has: daily-note dates are single-sourced per account — every paired or scanning device sees the same daily notes (one vault, possibly replicated by Obsidian Sync). Already implied by the dailyNotes LWW merge; stated here because note-scoped inference would misfire against per-device vaults with divergent daily notes.

### 3.11 The vault-format core is a shared package: @glance-apps/obsidian-format

Extracted ahead of Phase 6 (which requires the plugin's intent-apply side to run the SAME line grammar dayGLANCE runs — a lookalike parser maintained separately is the #1146–48 identity divergence re-seeded, permanently, across two codebases).

**The boundary principle: the package is format, never policy. It should not know an ownership rule exists.** It holds line identity (block ids, deterministic derivation, legacy hashing), decorations (completion markers, Tasks metadata, creation frontmatter), line building/rewriting (prefixes, the section sort, `updateTaskLines`), note naming (filename patterns, portability validators), the parser, and the heartbeat shape. It must never hold: transports, sync/merge, or any what-wins-on-divergence rule (3.10). The one seam where format brushes policy — `updateTaskLines`' write-time title guard — reports through the `onTitleConflict` callback and the CALLER resolves; that discipline is commented at the callsite because it is the erosion point.

**Repo/package plan (decided after checking Obsidian's actual submission requirements):** the community directory requires `manifest.json`, `README`, and `LICENSE` at the ROOT of the submitted repository and processes the manifest at HEAD of the default branch — so the plugin MUST get its own repo at submission time, and needs none of that during Phases 6–7 dogfooding (manual/BRAT installs work from release assets regardless of layout). Therefore: the plugin stays a dayGLANCE subdirectory through Phases 6–7; the package lives at `packages/obsidian-format/` under its FINAL npm name from day one, consumed by both dayGLANCE and the plugin via `file:` links (the plugin bundles it into `main.js`, so its shipped artifact is layout-independent); at the extraction event — directory submission — the package is published to npm and the plugin's new repo flips one dependency line. **Import specifiers never change across that move; that property is the point.**

**Test custody:** frozen-behavior pins travel with the code (the deriveBlockId goldens, the marker/metadata/frontmatter grammars, parse identity, `updateTaskLines` rewrite mechanics); policy tests stay in dayGLANCE (title-conflict resolution, per-field adoption, containment, surfacing, the transport round trips — including the no-op-write suite, which tests the transport's skip).

### 3.12 Pairing is a vault dead-drop under a one-time code

The plugin obtains its GLANCEvault credentials through the vault itself: dayGLANCE (on a device with direct vault access) seals `{vaultUrl, accountId, deviceToken, subkeyB64, pairingSalt, generation, createdAt}` into `.dayglance/pairing`, encrypted under a key derived (PBKDF2, same iteration count as the passphrase derivation) from a one-time code it displays; the user types the code into the plugin's pairing modal; the plugin opens the offer, verifies the token against GLANCEvault with one authenticated call, stores the credentials in `data.json`, and deletes the file. Cancel overwrites the offer with `{}`; offers expire after 10 minutes; a wrong code and a tampered offer are indistinguishable (both are a GCM tag failure).

**Rationale.** The vault is the one channel both sides already share on every platform, so pairing needs no server-side pairing endpoint (a surface that was considered and declined) and no copy-pasting of raw credentials. The steps a user takes are: click Start pairing, type one code — the token field is PREFILLED with the device's own GLANCEvault token, because on a shared-token server (the mode dayGLANCE uses; per-account enrollment exists in GLANCEvault but dayGLANCE doesn't use it) the bridge's token IS that token, and "mint a token for the bridge" was a step that didn't exist. The field stays editable for a separately-enrolled credential. Shared-mode consequence, recorded: the bridge's transport token is not individually revocable — revoking it means rotating the shared token on every device — while re-pairing still rotates the encryption subkey regardless.

**The code is 13 base32 characters (~65 bits) unconditionally — no same-device short-code path.** A third-party file syncer (iCloud Drive, Syncthing) can carry the offer file off-machine mid-pairing, so the offer must survive *offline* brute force for its whole lifetime; a convenience short code would quietly downgrade exactly the users who don't know their vault folder is synced.

**The per-pairing salt is what makes revocation real.** The bridge subkey is HKDF-derived from the root sync key with a RANDOM salt minted per pairing (info string `dayglance:bridge:v1`, namespaced apart from the sync engine's per-entity derivations). Revoke-and-re-pair therefore rotates the subkey, not just the transport token — a fixed derivation would leave a leaked `data.json` able to decrypt captured stream ciphertext forever. The salt doubles as the pairing `generation`: a vault copy whose synced `data.json` carries a different generation than a newly opened offer knows the offer supersedes it.

**Initiation is desktop/FSA-only, deliberately.** The dead-drop is a file, so the *offering* side needs direct vault access plus the root key — any normally-configured desktop or Chromium-FSA device qualifies. The native (Android/iOS) transports have read halves only and gained no write half for this; the platforms that lack direct access are the ones the *plugin* serves, and the plugin side of pairing (the modal) runs wherever Obsidian runs, mobile included.

### Phase 1. Launch-on-write — COMPLETE

Delivered by PRs #1435, #1444, #1445, and #1446; shipped with 4.7.0. See section 2.4. The scope and notes below are the as-built record.

**Goal.** When dayGLANCE writes to a vault while Obsidian is closed, launch Obsidian so Obsidian Sync pushes the change.

**Key insight.** No "sync now" command is needed. Obsidian Sync connects and reconciles as soon as the vault opens, so launching the app is the entire mechanism.

**Scope.**

- Fire `obsidian://open` after a debounced quiet window following vault writes. The URI form differs by platform:
  - **Desktop.** `?path=<absolute path>`. The `path` parameter overrides both `vault` and `file`, so no vault-name configuration is required. The absolute path is resolved in the Electron main process by `resolveInVault` and never reaches the renderer.
  - **Android.** `?vault=<name>&file=<relpath>`. Under SAF there is no absolute filesystem path — the bridge holds a content-tree URI — so `path=` cannot work. The vault name is derived programmatically from the tree URI, exactly as the existing `ObsidianBridge.openNote` does, so the outcome of no user-facing vault-name configuration still holds.
- **Debounce: 8 seconds, trailing edge, reset on every write — desktop only.** Any value in the 5-10 range is defensible. 8 is chosen because a leisurely triage session can have 5-plus second gaps between actions, which a 5-second window would split into multiple launches, while past 8 seconds nothing further coalesces in practice and the only effect is added latency. The cost asymmetry favors the upper-middle: an extra launch is nearly free (it focuses or no-ops), while added delay is invisible because the user is not waiting on it.
- **Android has no timer: writes arm the launcher, leaving the app delivers it.** Two forcing reasons, recorded so this is not relitigated. UX: an intent fired while the user is inside dayGLANCE brings Obsidian to the foreground and interrupts their flow — there is no Android equivalent of macOS's background `activate: false`. Correctness: since Android 10 the OS blocks activity starts from apps no longer in the foreground (the background-activity-launch restriction), so a timer expiring after the user left would be silently discarded — a timer-based Android launch only works when it interrupts, and fails exactly when the user edits and puts the phone away. The exit is the debounce: one delivery per session-with-writes, for the last-written note. Screen-off and incoming calls deliberately do not deliver (`onUserLeaveHint` excludes them); the armed state survives until a real exit and dies with the process.
- **Android delivery is split by exit path, and this too is platform-forced.** A back-button/gesture exit direct-launches: the app is the foreground actor performing a legitimate app switch, so the start is permitted. A Home or Recents press is different — it triggers the platform's `stopAppSwitches` suppression (built precisely so apps cannot hijack the Home button), and the deferred start is then dropped by the background-activity-launch check; verified on hardware, the `startActivity` is silently discarded. Automation apps clear this with the "Display over other apps" permission, which is too heavy an ask for this feature. The sanctioned channel is a quiet tap-to-open notification (LOW importance, constant id so re-posts update rather than stack, 15-minute timeout, retired on app resume and on a confirmed back-exit launch). Its tap `PendingIntent` targets Obsidian directly — Android 12+ forbids notification trampolines — so the tap cannot be observed, and the armed state is therefore only peeked, never consumed, by the notification path: an ignored notification does not lose the wake, and a later back-exit still direct-launches. **The offer is resolved on app resume**, which closes the one remaining gap: a tapped offer would otherwise leave the arm set and make the next back-exit open Obsidian redundantly. The tap is unobservable but its effect on the notification is not — gone from the shade means tapped, swiped, or timed out, all of which spend the offer, so the arm is consumed; still showing means merely ignored, so the arm survives and only the notification is retired. Because a back-exit is unreachable without first returning to the app, resolving on resume closes this completely rather than probabilistically. A resume is gated on an offer actually having been posted, so screen-off/screen-on — which fires `onStart` without any notification — cannot discard a valid arm, and the check degrades conservatively (treat as still showing, keep the arm) if the platform query fails.
- **Settings toggle must be device-local, not part of `obsidianConfig`.** `obsidianConfig` participates in cloud sync, and between non-native devices the incoming config wholesale replaces the local one. A `launchOnWrite` field inside it would leak from a Mac to a Windows machine and defeat the per-platform defaults. Use a device-local key (for example `day-planner-obsidian-launch-on-write`), which the `day-planner-` prefix rule captures in local device backups while excluding it from the cloud payload — the same posture as `darkMode` and `reminderSettings`. Store as tri-state, where unset means platform default, so changing a default stays a one-line edit.
- **Suppression when Obsidian is already running is deferred to Phase 5.** It depends on the heartbeat. Firing while Obsidian is open is harmless: on macOS `activate: false` makes it a no-op, and elsewhere it focuses the window.
- **Browser and PWA are out of scope,** and not merely by choice. A `window.open` fired from a debounce timer has no user gesture attached and is popup-blocked.

**Per-platform.**

| Platform | Mechanism | Default |
|---|---|---|
| macOS, all Electron builds | `shell.openExternal(uri, { activate: false })` from the **main process**, alongside the existing `obsidian:*` handlers | On |
| Windows Electron | `shell.openExternal`. Obsidian takes focus; no background equivalent | Off |
| Linux Electron | `shell.openExternal`. Handler registration is unreliable, especially for AppImage installs | Off, fail silently |
| Android | Armed by vault writes, delivered on app exit, split by exit path: **back-button/gesture exit direct-launches** (`ACTION_VIEW` via the existing `ObsidianBridge.openNote` path, from the back callback), while **Home/Recents exits post a tap-to-open notification** instead — a direct start there is impossible (see notes). **Not Capacitor** — `dayglance-android` is a native Kotlin WebView app with `@JavascriptInterface` bridges. No Tasker needed | Off |
| iOS | Not applicable until Phase 6 | n/a |
| Browser / PWA | None. Popup-blocked without a user gesture | n/a |

**Notes.**

- `activate: false` is macOS-only and works under the App Store sandbox, since it goes through LaunchServices rather than spawning a process. There was a historical period where it misbehaved when called from a renderer but worked correctly from the main process; the vault code is already main-process. Verify once on a real MAS build.
- Linux deep-link delivery and Linux vault access are independent capabilities and must not be gated on each other. Vault access works; URI handler registration may not.
- Optional polish: Advanced URI's `openmode=silent` avoids opening a tab. Detect its presence by checking `<vault>/.obsidian/plugins/obsidian-advanced-uri/` and the enabled list in `community-plugins.json`, and fall back to the base scheme when absent. A dependency to detect, never to require.
- **Write chokepoint: one per platform, on the native side of each bridge.** There is no single cross-platform chokepoint, and creating one in the renderer would be worse. On desktop, every write path funnels through `obsidian:write-file` in `electron/obsidian.ts`, which already holds the resolved absolute path and knows whether the write succeeded. On Android, the analog is `ObsidianRepository.writeText`, which `writeDailyNote` and `writeNote` share. A renderer-side debounce would require extracting a shared write helper across four inline `createWritable` sites plus the native wrappers, add a launch IPC back to main, and still not have the absolute path. Two small debounce policies, each at a real funnel with its own tests, is the smaller honest shape.
- **IPC surface is one channel:** `obsidian:set-launch-on-write` (renderer to main, boolean), pushed at startup and on toggle change. There is no renderer-invocable launch channel — main initiates the launch itself from the write handler, so the renderer never controls a URI. This preserves the security posture of the existing `obsidian:open-note` handler, where `setWindowOpenHandler` permits only http and https.
- **Lifecycle edges (covered, with tests):** a pending launch is cleared on toggle-off, on `obsidian:disconnect`, and on `obsidian:pick`, while the enabled flag survives a vault swap — so a launch never fires against a vault the user just swapped away from, and a write into the new vault schedules normally. On desktop app quit, a pending launch inside the quiet window fires immediately via a `will-quit` flush (fire-and-forget, so quit is never delayed); on Android the armed state dies with the process — the accepted-miss equivalent, since there is no exit hook left to fire from.

**Non-goals.** This does not solve propagation to other devices. It fixes the push side only. The pull side is Phases 5 through 7.

**Exit criteria (met).** Writing to a vault with Obsidian closed results in the change appearing on a second device without manual intervention on the originating machine — immediately on desktop and Android back-exits; after one notification tap on Android Home/Recents exits, where the platform forbids anything more automatic.

### Phase 2. Block-ID identity — COMPLETE

**Goal.** Give every dayGLANCE-managed task a stable identity in the vault that survives edits, reordering, and reformatting.

**Status.** Complete. Part A delivered by PR #1439; shipped in TWO releases per the staged-rollout rule (3.9): the **read release** (PR #1456) carried the full Part A read path — token recognition, `obsidian-dg-` adoption, the legacy bridge, first-occurrence-wins — with emission gated OFF; the **write release** flipped `OBSIDIAN_BLOCK_ID_WRITES` to `true` in `src/utils/obsidianWritePolicy.js`, backed not by an unenforceable propagation guarantee but by ghost-row containment (PR #1457) as the safety net for straggler clients, per the amended 3.9. Tokens already present in lines are preserved, never stripped. Phase 3 depends on this phase and is now unblocked. The scope below records the split and the semantics decided during implementation.

**Rationale.** Task identity is currently implicit, positional or text-matched. Every bug class fought in GLANCEvault (resurrection, phantom deletes, duplication) has a latent analog here and will surface as write surface grows. This is the highest-value single change in the plan.

**Scope — Part A (the whole deliverable).**

- Assign `^dg-<id>` block references on write: `- [ ] Review proposal ^dg-a1b2c3d4`. Format: 8 chars of lowercase base36, generated at write time, persisted on the task as `obsidianBlockId`, and embedded in the line itself — the vault carries the identity, so every device derives the same task id from the same line.
- **Ids are DERIVED, not random** (amended post-ship — the echo-stamp decision). The token is a pure function of the line's stable identity: 8 base36 chars of a frozen hash over (daily-note date, raw title as written) — the same inputs the legacy content id hashes, NFC-normalized and trimmed, computed only in the shared JS mint path (`deriveBlockId` in `src/obsidian.js`; the native layers never mint). **Why:** with random minting, an edit that reaches the fleet under the legacy id (it originated on a device without vault access, or a write failed before its rename committed) made every vault-capable device mint its own token for the same line — an N-way identity race that converged only through retirement records, detector reaping, and Obsidian Sync settling the file, with one no-heal corner: a mint whose device closed before ever scanning it lingered as a permanent duplicate row that ghost containment cannot catch (it is a well-formed tagged row). Derivation makes the race **semantically empty**: every device mints the same token, so an N-way mint is N devices writing an identical line — nothing to reconcile, nothing to reap, no coordination, no provenance tracking. **One logical edit produces one token by unanimity rather than election.** The alternatives — read-before-mint (already implicit in the tagged-line skip + write-success gating, and a no-op against the real timing) and origin-based mint suppression (real provenance machinery for a partial fix, with a trap variant that starves the vault of cloud edits) — are recorded in the decision discussion so they are not rediscovered. Derivation runs once, at mint time; the embedded token owns identity thereafter, exactly as before — this is not a return to content-derived identity. Existing randomly-minted tokens are untouched, the on-disk token shape is unchanged (no 3.9 read-release window), and the algorithm is frozen with golden-value tests: tokens derived by different app versions must agree forever.
- Match on read by ID first, falling back to existing text matching when a line carries no ID. The app-level id for a tagged line is the content-independent `obsidian-dg-<id>`; content-derived ids diverge across devices whenever two devices first import before/after an edit, so deriving from the block id is what makes cross-device matching converge. A one-time legacy-id bridge carries app-only fields across the switch.
- Migrate opportunistically: a task acquires an ID the first time a WRITE rewrites its line, committed to app state only when the write reports success. No flag day.
- IDs are assigned at write time in dayGLANCE and persisted, not derived at read time.

**Part B — deliberately not shipped.** A proactive sweep stamping IDs onto every existing line is a mass rewrite of the user's files; a bug in emission would corrupt everything at once, where Part A bounds any bug to one task. Part A converges on its own as tasks get edited, and untagged tasks keep working through the fallback indefinitely — there is no correctness cliff forcing a sweep.

**Decided semantics** (details and rationale in PR #1439):

- Duplicate `^dg-` ids (a line copy-pasted in Obsidian): first occurrence wins, vault-wide; later occurrences parse as untagged tasks.
- A tagged line retitled in Obsidian keeps its task, and the vault title wins when the line's raw title differs from what dayGLANCE last wrote; an unchanged line still preserves DG-side renames.
- A line ending in the user's own block ref (`^quote1`) is never stamped — Obsidian allows one block reference per line — but a line already carrying our id keeps it unconditionally.
- `obsidian-dg-` keys carry no date, and the deletion detector conservatively never tombstones undatable keys; a persisted sidecar (`day-planner-obsidian-last-scanned-dates`) supplies each key's last-seen daily-note date so deletion propagation stays alive for tagged tasks.

**Why block references specifically.** Native Obsidian syntax, invisible in reading view, survives edits and reordering, and linkable from anywhere in the vault.

**Note.** `^` is in the portability validator's rejected set for filenames. That is unrelated and correct; block IDs live in file content, not filenames.

**Exit criteria.** A task edited in Obsidian (retitled, moved between sections, reordered) is matched correctly on the next sync without duplication.

### Phase 3. Write-safety hardening — COMPLETE

**Goal.** Make vault writes safe against concurrent edits and partial failures before expanding what gets written.

**Dependencies.** Phase 2.

**Scope.**

- Content-hash change detection, so a sync cycle with no delta writes nothing. *(Delivered: a no-delta scan cycle was measured to already write nothing by construction; the remaining redundancy — the cross-device echo write — is closed by a byte-identity skip in both task write paths: when the would-be output equals what was just read, the disk write is skipped while the confirmed-write semantics are kept. The first echo after an Obsidian-side edit still writes, deliberately — the section sort normalizes the file once and steady-state echoes then skip; avoiding that first write would mean loosening byte-equality into semantic equality, i.e. changing what gets written, which this deliberately is not.)*
- Modified-since-last-read guard before overwrite, so an edit made in Obsidian between sync cycles is not clobbered. *(Investigated and DECLINED — recorded so it is not rediscovered as an open item. The pre-write read IS this guard, at the only granularity that matters and at the latest possible moment: every write path reads the file immediately before rewriting it, so "modified since last read" can only mean modified inside the read→write gap itself — single-digit milliseconds on desktop, ~10–50 ms through Android's SAF hops. The one surviving scenario needs Obsidian flushing a save into that gap ON THE SAME MACHINE (different machines write different vault copies), and even then Obsidian's editor re-saves its own buffer moments later and wins the file regardless, while the app-side state heals through the scan's completed-OR merge and the next writeback — permanent loss additionally requires Obsidian to quit before its next save. No transport offers compare-and-swap or locking, so the buildable minimum (a second read just before the write) closes only the compute microseconds of the window and buys effectively nothing; per-file mtime/hash state buys less (it was designed for write paths that don't read first, and all of ours provably do). The title dimension of the same race is separately closed by the write-time title guard below. WATCH SYMPTOM that would reopen this decision: text typed in Obsidian vanishing from a daily note whose task line just changed state on the same machine — seen more than once, it means the window is wider than analyzed, and the likely real culprit is a STALE READ BASIS (a transport serving cached reads), which wants a read-freshness fix on that transport, not this guard. Obsidian conflict banners or Sync conflicted copies clustering around dayGLANCE write times would point the same way.)*
- Verify write atomicity per transport. FSA's `createWritable()` provides atomicity by default via a swap file and rename. The Electron main-process path and the Android SAF path need explicit verification. *(Delivered: Electron temp+fsync+rename; Android temp/delete/rename with deterministic recovery; iOS was atomic all along; the write/read failure contracts and their surfacing shipped alongside.)*

**The two-sided retitle policy** (decided; `src/utils/obsidianTitleConflict.js`; ownership ruling 1 — see 3.10). A tagged task retitled in dayGLANCE **and** in Obsidian between syncs is detected by a three-string comparison — base = `obsidianRawTitle` (the vault line at our last successful observation, honest since the write-success contract), theirs = the parsed line now, ours = the app title stripped of the display tag; a conflict is both sides off the base, to different texts. Resolution: **the vault wins the title; the dayGLANCE rename is preserved as a durable record appended to `task.notes`** (idempotently — the record text is deterministic, so N devices' scans collapse to one line), plus a fire-and-forget neutral toast. A **write-time guard** funnels the write-first interleaving into the same single policy point: `updateTaskLines` compares the matched line's current bare title against the base and, on divergence, writes the state change while keeping the *line's* title (a state write must never revert an Obsidian retitle — that clobber destroyed its own evidence); if a retitle was also in flight it signals the conflict and the writeback skips the `titleUpdate` commit, so the base stays truthful and the next scan (≤5 min) resolves it — a delay, never a loss. The notes field is app-only and outside the writeback's change detection, so preservation can never itself trigger a vault write.

**The guard also protects one-sided vault retitles** — a behavior in its own right, not just a conflict funnel. Before the policy, *any* state write onto a tagged line rebuilt it from app state: completing a task in dayGLANCE within the scan gap after retitling its line in Obsidian silently reverted the retitle — a one-sided clobber needing no dayGLANCE rename at all, and the more common interleaving. Under the guard, a plain state write (completion, reschedule, time change) onto a line whose title has moved off the base keeps the **line's own title**, writes only the state, and stays silent — no conflict signal, no notes record, nothing two-sided happened; the next scan adopts the vault title through the ordinary one-sided `vaultTitleWins` path. This follows directly from the mismatch rule ("on divergence, keep the line's title") and is pinned by its own tests: the pre-policy test that asserted the clobber (`obsidian.blockIds.test.js`, "matches by id even when the title was edited in Obsidian") now asserts the line's title survives, with a comment recording the flip.

**Why this shape (recorded so it is not relitigated).** A conflict is a one-shot event, not a persisting condition — nothing broke, nothing retries, no recovery to await — so the failure-surfacing latch is the wrong channel: latched, a notice either evaporates before the user looks or squats on the error state blocking real failures, and it should not be red at all. The durable record belongs on the task, where the user will be looking when they notice the title is not what they typed. Rejected alternatives: **vault-wins-made-visible alone** (its honest version still wants somewhere durable for the old title, at which point it is this policy); **dayGLANCE wins** (reverts the user's edit in their own vault — hostile); **timestamp LWW** (built on sand: there is no per-line vault edit time, **file mtime on a synced vault reflects Obsidian Sync delivery, not edit time**, and clock skew applies — it would resolve confidently and sometimes wrongly, which is worse than not resolving); **conflict UI** (wrong cost/benefit for an event this rare). Untagged lines need no policy: they match by title equality, so a diverged untagged line simply re-imports under a new identity — the pre-existing benign behavior.

**Exit criteria (met).** An edit made in Obsidian while dayGLANCE is running is never silently lost: atomicity per transport, the write and read failure contracts with surfacing, the two-sided retitle policy with its write-time guard, and the no-op write skip together close every identified loss channel; the declined guard's residual window is the same-machine sub-10 ms whole-file race documented above, dominated by Obsidian's own last write and self-healing in the app. Phase 4 is unblocked.

**Goal.** Speak the formats Obsidian power users already use, so dayGLANCE content is queryable with their existing tooling.

**Scope.**

**Rationale.** This is the cheapest real user-facing win in the plan and the thing that makes a directory listing compelling to someone already living in their vault.

**Plan of record (decided after the Phase 4 investigation) — three steps:**

2. **Tasks-emoji + Dataview-inline READ — COMPLETE (as-built record).** One trailing-metadata extraction over both serializations (`utils/obsidianTasksMetadata.js` — the Tasks plugin itself has a dataview-format mode, so reading only emoji misses half its users), under the IDENTITY-FROZEN design: `obsidianRawTitle` keeps the full line text on EVERY line, tagged or untagged — extraction is non-destructive, which is why it safely applies universally, unlike #1470's completion-marker strip (dayGLANCE's own regenerated decoration, tagged-lines-only). Only the display title is stripped. Mapping as confirmed: due→deadline (📅-only lines stay inbox), scheduled→the timeline (date-only → all-day; a line's own time prefix supplies the time; an explicit inline date prefix WINS over ⏳ — it is dayGLANCE's own reschedule channel), priority→0–3 with the recorded collapse ({highest,high}→3, medium→2, {low,lowest}→1 — display-side and reversible, the vault text is frozen and never written back), ✅→completedAt stays #1470's channel (a non-trailing ✅ or [completion:: …] is display-stripped, never mapped — no second vault-derived completion channel). 🛫 and unknown Dataview keys: preserved as text, mapped to nothing. 🔁 recognized, NOT mapped — no write-behavior change, no decline, no warning (decided) — but BADGED on the task card, so "completing here won't create the next instance" is a visible property instead of a silent surprise. Vault-side edits after import adopt at FIELD grain per ownership ruling 2 (see 3.10). The retitle-metadata-carry wrinkle was real and is built: a DG rename re-attaches the line's verbatim metadata segment (`reattachTasksMetadata` — the same helper the title-conflict resolver's comparison uses, so comparison space and written bytes cannot diverge), a deliberate write-path change inside read support. Two shipped-code hazards were closed with pinned tests: the comparison-space split (display `ours` vs full-line `base` would have made every metadata-carrying task read as permanently renamed — conflict-note spam on every vault edit) and the display-derivation bridge (unrenamed old-style titles shed their in-title metadata on the next scan; genuine renames untouched).
3. **Emoji/Dataview WRITE — deferred indefinitely, for SEMANTICS, not rollout risk.** The investigation predicted rollout risk here and was wrong: containment turned out to be inherited via the `^dg-` token (see 3.9's standing consequence), so writing these formats is rollout-SAFE. ### Completion timestamps in the vault — feature record (its own item, not a Phase 4 step)

**Goal.** When dayGLANCE completes a task, the completion date reaches the vault line, in whichever format fits the vault — so completions are queryable with the tooling the user already runs.

**What it required first (the buried lede, approved deliberately).** dayGLANCE did not record completion times for scheduled tasks — nearly every vault task. The scheduled completion branch deliberately set no `completedAt` for years, and that absence was pinned by name in `taskMutations.pinning.test.js`. This feature is therefore "start knowing it, then write it," not "write what we know": **both completion branches now stamp `completedAt`, as a full ISO datetime with the local UTC offset** (`completionTimestamp()` in `utils/taskUtils.js` — local-offset so `slice(0, 10)` of the stored string is the user's local date at the moment of completion; an evening completion in the Americas must not read as tomorrow). The two pinning tests flipped from asserts-absent to asserts-present — the visible mark of the contract change. Historical date-only values are left as they are and emit honestly as dates; no fabricated midnight times.

**Format selection — vault-level, at write time only.**

- Tasks plugin enabled → `✅ YYYY-MM-DD` (date only, the plugin's own convention).
- Otherwise → `[completed:: <stored value>]`, a Dataview inline field (date or datetime, whatever `completedAt` holds).
- Detection reads `.obsidian/community-plugins.json` (a flat array of enabled plugin ids; the Tasks plugin is `obsidian-tasks-plugin`), per transport: FSA and the Electron shim reach the dotfile directly; Android and iOS gained a `getCommunityPlugins` bridge method under the shared read contract (`""` = determinately absent, null = read failed). **Failure default: not-Tasks → the Dataview field** — the safe direction twice over (a vault with no community plugins legitimately has no such file, and a wrong guess is cosmetic: Tasks ignores unknown inline fields, Dataview still indexes). An undetermined answer (old native shell, failed read — including the legacy iOS shell's `"null"`-string echo, the string-transport trap again) keeps the last persisted answer instead of flapping the format. Detection refreshes once per sync cycle and never blocks or fails a write.
- **Deliberately dynamic and churn-free.** The format is chosen at write time; nothing ever rewrites historical lines for a detection change. A line adopts the current format the next time its task changes anyway; the no-op write skip guarantees a detection flip alone rewrites nothing; a mixed-format vault converges per-touch and is stable, because **both formats are always recognized at parse regardless of current detection** — otherwise toggling the plugin would turn old markers into title text and manufacture divergence.

**Identity scoping — the slice of the Step 2 identity-freeze design that had to land here.** The marker is split off at parse on `^dg-`-tagged lines only, absorbed into `completedAt` when the line is checked. Untagged lines stay byte-frozen: a hand-written `✅ …` there remains title text and part of the legacy content-derived identity, exactly as before. Every line dayGLANCE writes a marker to is tagged (writes stamp), so the strip covers exactly the lines that need it. On the write side the marker is a **regenerated suffix** — like the `^dg-` token, never part of the stored title — sitting between the title and the token (`- [x] Title ✅ 2026-08-28 ^dg-abc12345`; the token stays absolute end, matching both Tasks' conventions and the parse order). Regeneration is byte-deterministic from the stored `completedAt` string, never recomputed from "now" or a local timezone at emit — so N devices regenerating the same state emit identical bytes and the no-op skip holds. Re-completion **replaces** and uncompletion **removes** with no dedicated machinery, because there is nothing to append to. `updateTaskLines` splits the marker off before every title comparison, so the write-time retitle guard operates on clean titles and completing a marker-bearing line never reads as a vault retitle. A hand-written marker on an untagged line being stamped for the first time normalizes out in the same write (one-time); a line that cannot be stamped (foreign trailing block ref) is left byte-frozen and gets no marker — a marker the parse could never strip would silently change the line's identity.

**The merge rule (approved deliberately; ownership ruling 3 — see 3.10): app wins when it has a value; the vault marker fills the blank.** The apparent inconsistency with the title policy dissolves on inspection: a title is user-authored content, so the vault is ground truth for titles — but a completion timestamp is dayGLANCE's own record of an action dayGLANCE performed, and the vault marker is an echo of it. Letting a stale echo overwrite the source would be backwards. The adoption case — vault has a marker, app has none — isn't a conflict at all; it's importing data we lack. An explicit null (the app uncompleted the task) is the app's statement and still wins. Implemented where the app-field carry already lived (`preserveObsidianAppFields` in useObsidianSync), so the rule is one spread, not new machinery.

**The setting (approved: yes, default ON) — and where it could NOT live.** "Write completion dates to Obsidian" is aesthetic, not correctness — nothing breaks either way, and the vault minimalist who wants pristine `- [x] Buy milk` lines is real — so a user-facing toggle is legitimate under 3.9's own distinction (the CORRECTNESS gate stays a build-time constant; see below). It was intended for `obsidianConfig`, but verification killed that: **`obsidianConfig` is device-local on every merge tier** (`ALWAYS_LOCAL_KEYS` in mergeSync.js, `ALWAYS_DEVICE_LOCAL` in sync/dbAdapter.js — the vault genuinely differs per machine), so a field there would never propagate, and per-device values would make devices fight over marker presence per-touch. The setting is therefore its own **synced top-level key `obsidianCompletionDates`** (+ `UpdatedAt` sibling), riding the `habitsEnabled` pattern on both tiers: LWW across a single user's devices, kept device-local under multi-user so one household member's choice doesn't flip everyone's vault convention. The file-tier slice-coverage canary enforced the full plumbing. OFF converges vaults clean **per-touch, never via a sweep**: rewrites strip an existing marker and regenerate nothing; reading both formats stays unconditional.

**3.9 relationship — a recorded single-release deviation.** This is the first written line-level format since 3.9 recorded the `^dg-` token as the universal self-identifying carrier, and it ships read+write in one release rather than staged. Grounds: markers are emitted only onto tagged lines, so an old client's misread is self-identifying from day one — marker and token swallowed together into a mangled title whose trailing token still names the successor — and containment is inherited unchanged (the decorated-ghost case was added to the containment tests per 3.9's standing obligation, and passes by inheritance as predicted). The exposure is exactly the bounded, temporary, self-healing inconvenience the block-id record already accepted. The staging option remains one flip away: emission is gated by `OBSIDIAN_COMPLETION_MARKER_WRITES` in `utils/obsidianWritePolicy.js` (build-time, per the standing rule), independent of the user setting.

**Explicitly not in this feature.** 🔁 recurrence behavior is untouched (no decline, no warning — decided; the recurrence badge is Step 2 scope). No Tasks lifecycle semantics: the marker is a decoration regenerated from app state, never a trigger for next-instance creation. No read support for the rest of the Tasks/Dataview metadata surface — that remains Step 2 under the full identity-freeze design.

### Phase 7. Live sync — COMPLETE

**Goal.** Near-real-time propagation while Obsidian is open.

**Dependencies.** Phase 6.

**Scope.**

- Plugin holds an SSE connection to GLANCEvault while Obsidian is open, applying changes as they arrive.
- Desktop only in practice. Mobile gets drain-on-open per section 5.
- Self-nudge loop prevention: the plugin applying an inbound change must not emit that change back outbound. This is structurally the same failure identified in the lastGLANCE SSE audit; use lifeGLANCE's persisted-flag pattern.

**Exit criteria.** A change made in dayGLANCE on one desktop appears in Obsidian on another within seconds, with no echo.

**Build record.** Two halves, one channel: the dayGLANCE-side inbound nudge landed first (#1494 — bridge-row `/events` nudges wake the observation cycle, paced by probe + min-gap), and this build closes the outbound leg — the plugin consumes the SAME seq-only `/events` stream to drain intents on arrival instead of waiting out the 30-second timer. Decisions of record:

- **THE CREDENTIAL INVARIANT: SSE is armed by proof and disarmed by refutation** — the stream opens only after a successful authenticated drain, closes on auth failure (401/403 at connect or from a drain) or a vanished pairing, and makes zero reconnect attempts in between; a de-paired plugin burns nothing. The 30-second drain tick is both the correctness floor for missed nudges AND the re-arm mechanism (the first drain that succeeds re-proves the credential), so a dead credential's total cost is polling's own benign failure mode: one failed drain per tick. Built for an observed failure, not a hypothetical — the 2026-08-31 plugin-settings-sync incident (§3.2's recorded dependency) silently stripped a device's pairing out of `data.json`.
- **Transport is Node `http(s)`, deliberately**: Obsidian's `requestUrl` buffers whole responses and cannot stream SSE (the same limitation that made the mobile shells grow native readers), and renderer `fetch` enforces CORS, which would couple the stream to the server's `allowedOrigins` containing Obsidian's `app://` origin. Node's module has neither problem, and its availability (`window.require`, Electron renderer only) is a structural desktop gate alongside `Platform.isDesktopApp` — mobile cannot take this path even if the platform probe were wrong.
- **The pure/wiring split is the build's shape** (a condition of the commission, same reason as normalize-then-observe): every decision the transport makes is pinned in `@glance-apps/obsidian-format`'s `bridgeSse.js` — the frame parsers (moved verbatim from dayGLANCE's `vaultEventStream.js`, which now re-exports them, so the one wire format has one parser), the arm/disarm state machine, the own-ack skip, the debounce/seq-cursor nudge gate, and the backoff schedule (5s doubling to 60s, reset on any received frame; ~60s read timeout = three missed server heartbeats, the detector for sleep and silent network loss on weeks-open machines). `bridge.ts` keeps only connection lifecycle and Node plumbing.
- **Self-nudge safety is layered**: the exact-ack own-seq skip (both write paths return their resulting seq; one nudge per write operation — dayGLANCE's `ownWrites` principle, miniaturized) makes own echoes free, and beneath it the by-construction argument: a nudged drain's idle path performs no writes, so no cycle can sustain itself. **That argument leans on #1485's tombstone-is-cursor-movement-only rule and is annotated as such at both sites** — a future change to that rule invalidates this reasoning with it. A nudge landing while a drain is in flight sets a rerun flag instead of being dropped by the `draining` guard (the #1494 hazard, same fix).
- **Rate budget**: an SSE connection costs one request at connect; heartbeats and nudges are free; reconnects are one each, bounded by the backoff (worst-case flap ~12/min at the floor) and further extended by the shared 429 brake. Server-side caps (64/account, 1024 total) are generous for a household fleet.
- **Idle-nudge cost** (the shared account seq carries other apps' activity): one empty app-scoped list per debounced foreign nudge — the drain is its own probe, since `/sync/:app/list` returns only bridge-namespace rows. A future glance-vault `app` tag on activity frames would reduce this to zero and let dayGLANCE's #1494 probe be deleted; deliberately not built against (backward-compatible when it comes — both consumers ignore unknown frame fields).

**Post-build amendment (2026-08-31).** Phase 7's own machinery held, but its SPEED invalidated three guards elsewhere that were implicitly sized to poll cadence, producing the SSE-speed cross-device war on day one of dogfooding — the full record, the three fixes (buffer-safe intent applies, the wall-clock confirmation hold, the retirement-heal breaker), and the cycles-versus-wall-clock lesson live in §3.10's ruling-7 correction record. Phase 7 itself is unchanged by the fixes; what changed is that the guards around it now measure the things they actually wait for. *Amended again later that night:* the third speed-revealed incident (the db-tier retire/tombstone war — §3.10's seventh record) was a NEW CLASS, which is what the assessment's tripwire was set for: dayGLANCE's SSE nudge consumption is now gated OFF BY DEFAULT (`sseNudgesEnabled`; `dayglance-sse-nudges` = `on` to re-arm for a supervised test) until that war's breakers are proven. The plugin's SSE and all of Phase 7's machinery remain built and unchanged — the retreat is one flag, exactly as priced.
